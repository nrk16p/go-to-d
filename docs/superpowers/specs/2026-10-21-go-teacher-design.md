# Go-to-D: a joseki sparring teacher — design

Date: 2026-10-21
Repo: github.com/nrk16p/go-to-d (empty before this doc)

## Why

The owner is a kyu-level Go player working toward a **4 kyu rank test**. The test (as far as
research could find for Thailand) is played as real games against examiners with handicap
stones — not a written quiz. So the site has to make them play better corners in real games,
not just recognise diagrams.

They want it to feel like **a 3-dan teacher who plays against them and corrects them** —
not a database to browse and not a fixed lesson that plays the same every day. They rejected
a "fixed daily lesson" framing; what they want is sparring with feedback.

This is a personal site for one person. No accounts, no other users.

## Goals

1. **Corner sparring.** The teacher plays one side of a corner, the owner plays the other,
   and every owner move is judged on the spot.
2. **Joseki course of ~100 patterns** across the corners the owner named:
   4-4, 3-3, 3-4 and 4-3 (4-3 is the mirror of 3-4 — one family, shown in both orientations).
   Each pattern can be practised from the **attack** side (approaching / invading) and the
   **defend** side (owning the corner).
3. **Correction that teaches.** A mistake stops play, shows the better move, says roughly how
   many points it cost, and — when the book covers it — explains *why* in a teacher's voice.
4. **Variety.** The teacher picks different branches each time so the owner can't pass by
   memorising one line.
5. **Off-book play is still judged.** If the owner plays a move the book doesn't cover, a real
   engine (KataGo running in the browser) judges it and answers it.
6. **Memory over days.** Patterns the owner misses come back sooner (simple spaced repetition).
   A home screen shows what's due today and progress through the 100.

## Non-goals (for this version)

- Full-board games against the AI (handicap games like the real test) — planned next, not now.
- Life-and-death / tesuji problems — planned later.
- Natural-language explanations generated by Claude/LLM — needs an API key; later, optional.
- Thai language — English first; Thai later.
- Accounts, login, sync between devices, multiplayer.

## Anti-goals (would be a failure even if it "works")

- **Teaching wrong or outdated joseki.** Every book move must be checked against the engine
  (see "Book verification"). Prefer modern, AI-era lines over pre-2016 lines that AI now
  considers bad.
- **Too slow to use.** If the teacher takes more than ~5 s to answer on a phone, it isn't usable.
- **Robotic or AI-sounding teacher.** Notes must read like a stronger friend talking: short,
  direct, concrete ("Block from this side — your wall faces your other stone.").
  No "This move is optimal because…", no filler.
- **Memorising without understanding.** Every book move has a reason attached; quizzes ask
  for the move, but feedback always gives the reason.

## Constraints

- **Static site**, hosted free on **GitHub Pages** from the `go-to-d` repo. No backend server.
- Works on **computer and phone** browsers (touch-friendly board, phone width with no
  horizontal scroll).
- **Engine runs in the browser.** KataGo's network runs client-side. First download
  should stay roughly **≤ 40 MB**, cached after that (Cache Storage / service worker).
  A GitHub Pages single file must stay < 100 MB.
- **Progress lives in the browser** (localStorage, every read/write wrapped in try/catch so a
  private window still works) plus a manual **Export / Import progress (JSON)** button as
  the backup, since browser storage can be wiped.
- Repo is public — never commit secrets (none are needed for this version).
- Licences: KataGo weights and the known browser ports (kaya-go ONNX conversion,
  Sir-Teo/web-katrain) are MIT. Joseki notes are written fresh — never copy text from books
  or other sites.

## What the owner decided

- Joseki first, organised by 4-4 / 3-3 / 3-4 (+4-3 mirror), attack and defend.
- About 100 patterns.
- The teacher **plays against them and corrects them** (sparring), rather than a fixed lesson.
- A real engine judges moves outside the book.
- English for now.

## How it works

### 1. The joseki book (data, authored)

A versioned data file (JSON or TS) describing a **tree per starting position**.

- **Pattern** = a named main line from a starting position to a settled shape, e.g.
  "4-4 · low approach · knight's-move answer · slide · extend". ~100 patterns total.
- Suggested split (builder may rebalance, keep ~100):
  - 4-4 star point, approaches and responses — ~30
  - 3-3 invasion under 4-4 (both sides) — ~15
  - 3-4 / 4-3 komoku, approaches and responses — ~45
  - 3-3 point as the corner stone — ~10
- Each **node** (a move) carries:
  - coordinates, colour
  - `note`: the teacher's one- or two-line reason (owner-facing copy)
  - `kind`: `joseki` (normal), `alternative` (also fine), `mistake` (common kyu error, with
    its punishment line as children), `trick` (trick play the opponent may try)
  - optional `tenuki` (playing elsewhere is a legal answer at this node)
  - optional `weight` for how often the teacher chooses this branch
- Each pattern has: id, family, name, starting stones/setup (usually just the corner on an
  otherwise empty board; a pattern may add a few stones, e.g. a pincer context),
  difficulty (1–3), and frequency rank (common patterns first in the course).
- "Tenuki" (play elsewhere) is a real move: both the owner and the teacher can choose it
  when the book allows.

### 1b. Patterns vs. the shared tree (my call)

- The book is **one shared tree per starting position**; a **pattern is a named path** through
  it (start → leaf). Review state is keyed by `patternId × side`.
- Two session modes:
  - **Drill a pattern** — the teacher stays on that pattern's path. If the owner plays a
    different move that is still in-book `joseki`/`alternative`, it's not marked wrong:
    "Fine, that's joseki too (→ pattern name) — but this drill is the knight's move." Buttons:
    **Retry this drill** / **Switch to that pattern**. No penalty either way.
  - **Free sparring** ("Teacher's choice") — the teacher picks branches by weight anywhere in
    the tree. Credit/penalty goes to the pattern(s) whose path was actually played (the
    deepest named path reached).
- A mistake on an early move shared by several patterns counts only against the pattern being
  drilled (drill mode) or the pattern actually reached (free mode) — never all of them.

### 1c. Whole-board context (my call)

- Corners are never played on a fully empty board. Each family has a small **default setup**:
  stones in the other corners (e.g. star points as in a handicap game, or a common even-game
  opening), so direction of play ("your wall faces your other stone") is meaningful.
  A pattern may override the setup (e.g. pincer context, ladder breaker).
- The 4 kyu test is played as handicap games, where the owner is Black on star points, so the
  4-4 family (approaches to 4-4, 3-3 invasions) gets more weight in course order. The 3-4/4-3
  family stays in, because the owner asked for it and meets it in even games.
- Book check and in-session judgement compare a move against the **best move in the corner
  region**; "tenuki" is evaluated separately as one more candidate, so standard finishing
  moves aren't flagged just because an empty corner elsewhere is bigger.

### 1d. Build order (my call)

- **Phase 1:** sparring loop + engine + ~20 most common patterns (4-4 approach/slide/extend,
  3-3 invasion lines, basic 3-4 approaches), fully checked. Usable on its own.
- **Phase 2:** grow the book to ~100, Library screen, review scheduling polish.
- Book notes: engine checks moves, not the written reasons. Each note is written against the
  engine's main line for that position, and any note the author is unsure of is marked
  `confidence: low` so it shows a small "check with a stronger player" hint.

### 2. The engine (KataGo in the browser)

- Runs in a **Web Worker** so the board never freezes.
- Gives, for a position: best moves, win-rate / score estimate, so we can compute
  **points lost** by the owner's move vs. the best move.
- Search is restricted to the **corner region** (that quadrant plus a margin) plus a
  "tenuki" option, so the teacher doesn't wander off to another corner unless tenuki is
  correct.
- Rules/komi: area scoring, komi 7.5 (only matters for score estimates).

### 3. A sparring session

1. Owner picks a family + side (attack / defend), a specific pattern, or "Teacher's choice"
   (picks due reviews first, then the next new pattern).
2. Board shows a 19×19 board zoomed to the corner being played.
3. Teacher plays its side. In-book, it chooses among branches by weight (and favours branches
   the owner has missed before). Off-book, the engine chooses.
4. Owner plays. Judgement:
   - **In book, joseki/alternative** → short "Good —" note, play continues.
   - **In book, `mistake`** → stop: show the better move, points lost (engine), the book note.
     Buttons: **Retry** / **Play on** (teacher then plays the punishment line).
   - **Off book** → engine judges. If points lost is small (threshold, e.g. ≤ 1.5) → "Fine,
     not the usual move, but it works", show the book move for reference. If bigger → stop,
     show the engine's better move and points lost, Retry / Play on. Play on = engine answers.
5. Session ends at the pattern's settled shape (book leaf), after the engine says the corner is
   settled / a few moves past leaving the book, or when the owner stops.
6. **End report**: moves right / wrong, points lost in total, the patterns now due for review.

Thresholds (points lost for "fine" / "mistake" / "big mistake") are settings with sensible
defaults.

### 4. Memory and progress

- Each pattern × side (attack/defend) has a review state (Leitner boxes or similar):
  clean run → longer gap; any mistake → back to short gap.
- **Home ("Today")**: patterns due for review, the next new patterns (about 2 new per day as a
  default suggestion, not enforced), streak, mastered count out of 100 (×2 sides).
- **Library**: browse all patterns by family, see the main line with notes, jump into sparring.

### 5. Teacher voice (copy rules)

- English, short sentences, concrete, like a 3-dan friend sitting next to you.
- Say what the move does and why; mention whole-board direction when it matters.
- No AI-sounding phrasing, no hype, no "optimal"/"it is important to note".
- Mistake notes say what goes wrong in concrete terms ("White cuts here and both your stones
  are weak").

## Book verification (protects against wrong joseki)

- Every book line is checked by script against KataGo (native KataGo on the Mac is fine for
  this, or the same in-browser engine run under Node):
  - each `joseki`/`alternative` move should be within ~2 points of the engine's best move
    in that position; anything worse gets flagged for review,
  - each `mistake` move should actually lose noticeably (else it isn't a mistake),
  - all moves legal; captures handled correctly by the rules code.
- The check runs as a test and in CI, so a bad edit to the book fails the build.

## Calls made for the owner (owner said "design for me all")

- **Phone/browser:** unknown, so support **both iPhone Safari and Android Chrome**. The engine
  runtime must work on Safari (WASM path required; WebGPU only as a speed-up when present).
  The site is an installable **PWA**; on iPhone the Home screen shows a one-time hint to
  "Add to Home Screen", because Safari can wipe storage/cache after 7 days without a visit.
  Export/Import progress stays as the safety net.
- **Test date:** unknown, so ship in phases (see 1d): Phase 1 is a usable sparring teacher
  with the ~20 most test-relevant patterns.
- **Test format:** assume handicap games with the owner as Black on star points → the 4-4
  family (approaches to 4-4, 3-3 invasions, from Black's defend side first) leads the course;
  attack-side and 3-4/4-3 follow.

## Left to the builder

- Front-end framework and build tool (my call as default: Vite + TypeScript; React is fine).
- Exact KataGo network and runtime (ONNX Runtime Web with a kaya-go-style conversion, or a
  TF.js port like web-katrain loading `.bin.gz` weights) — pick by a quick spike that measures
  download size, phone speed and strength. Target: answers a corner move in ≤ ~3 s on a
  recent phone, strong enough to judge a 4-kyu (low-dan or better with a small search).
- Search size (visits) per move, and the corner-region restriction details.
- Board rendering (SVG or canvas), coordinate display, sound.
- SRS algorithm details and default thresholds.
- Visual design (calm, readable, works in light and dark).
- GitHub Pages deploy via Actions.
